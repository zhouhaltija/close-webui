# Spec Delta

## Purpose

定义用户发送后的即时反馈、流式展示的可测量响应和可靠保存边界，避免空对话页面等待，同时确保停止、错误、刷新和用户切换不会因性能优化丢失消息或复活旧生成。

## ADDED Requirements

### Requirement: 即时提交反馈
系统 SHALL 在有效提交后 100ms 内显示用户消息预览和助手提交状态，不等待网络或数据库成功才显示，不在新对话创建后闪现空对话欢迎页。

#### Scenario: 慢建对话与慢生成提交
- **WHEN** 创建对话、生成提交或首字分别延迟数秒
- **THEN** 消息预览立即可见；提交成功前表示正在提交，确认后表示等待模型响应，不虚称已保存或已收到正文

#### Scenario: 拒绝与不确定提交
- **WHEN** 创建失败、生成被拒绝或请求断开而提交结果不确定
- **THEN** 给出明确状态并保留可恢复输入；通过原消息和生成 ID 对账，不重复用户消息，不使用普通失败重试覆盖未确认的提交

### Requirement: 流式响应与渲染
系统 SHALL 连续合并已确认的正文增量，只更新必要的展示内容；高频输入下使用有界缓冲，不重复渲染所有历史消息或为每个字符重复执行完整代码高亮。

#### Scenario: 受控流式基准
- **WHEN** 已预热仿真上游持续每 50ms 输出正文，使用独立测试 schema，并测量单次持久化往返
- **THEN** 上游正文到服务端 Flush 的额外延迟 p95 不超过一个持久化往返 p95 加 100ms；在往返不高于 100ms 时不超过 200ms，报告浏览器展示延迟和原基线比较

#### Scenario: 长内容与首字
- **WHEN** 输出包含两万字符、代码块、表格和较多旧消息
- **THEN** 首个正文不等待凑满大批次；预热后增量渲染耗时 p95 不超过 32ms，旧消息渲染次数不随每个增量增长，用户向上阅读时不被强制拉到底部

### Requirement: 持久化与终态完整性
系统 MUST 继续先保存正文增量再发送，保存全部剩余内容和终态后再发送 done 或 error；未确认保存的上游文本不能被伪装为持久正文。

#### Scenario: 写入缓慢或失败
- **WHEN** 数据库写入变慢、失败或上游提前结束
- **THEN** 使用有限缓冲和背压，不能提前发送成功；刷新恢复最后确认内容，所有已显示的正文都可以从数据库读取

#### Scenario: 停止删除及迟到渲染
- **WHEN** 用户在提交前、首字前或流中停止，删除对话、退出、切换账号或服务重启
- **THEN** 停止上游；数据库迟到写入、待发送批次与浏览器待绘制增量均不能恢复旧生成，原消息顺序和快照重试不变

### Requirement: 可追溯的性能证据
系统 SHALL 区分本地反馈、数据库提交、上游连接/首字、持久化及浏览器渲染的耗时，不将付费供应商思考时间或测试断言等待时间当作系统改进证据。

#### Scenario: 审核交接
- **WHEN** 实施者宣称修复发送或流式卡顿
- **THEN** 提供固定输入、仿真节奏、样本数量、数据库往返、p50/p95 和修改前后对比，日志不包含密钥、密码、完整会话或私人聊天正文
